# Interview Notes

本文档用于沉淀求职时可以讲清楚的项目要点。

它不是学习流水账，而是面试官视角下的“我做了什么、为什么这样做、后续如何扩展”。

## 项目一句话介绍

```text
这是一个使用 Unity 2D 和 C# 实现的单人版炉石核心对战原型。
当前阶段完成了卡牌数据、玩家资源、战场、回合流程、随从召唤、基础伤害法术、随从攻击随从、随从攻击英雄、胜负判定、第一版 UGUI 显示交互、冲锋、嘲讽、战吼、第一版事件系统、亡语、圣盾，以及基于合法动作枚举、快照模拟和评估函数的单人 AI 对手。
```

## 架构亮点

### 1. 静态数据和运行时状态分离

项目中把卡牌拆成：

```text
CardData：静态模板
Card：手牌/牌库里的运行时卡牌
Minion：场上的运行时随从
```

面试表达：

```text
我没有直接修改 ScriptableObject 里的模板数据，而是用 Card 和 Minion 保存对局中的运行时状态。
这样同一张卡可以在牌库里出现多份，后续也可以支持减费、受伤、Buff 等运行时变化。
```

### 2. Core 和 UI 分层

当前 Core 层不依赖 UI。

```text
Core 负责规则。
UI 负责显示和输入。
```

面试表达：

```text
UI 不直接扣法力、不删除手牌、不修改战场。
玩家点击后，UI 只调用 GameManager 的规则方法，然后重新读取 Core 状态刷新显示。
这样规则层更容易测试和扩展，也避免 UI 和规则混在一起。
```

### 3. GameManager 作为阶段性调度器

当前 `GameManager` 负责：

```text
开局
回合切换
出牌
攻击
死亡清理
胜负判断
```

面试表达：

```text
阶段 1 为了快速完成最小可玩原型，我先让 GameManager 承担主要流程调度。
阶段 2.1 的基础伤害法术也暂时由 GameManager 直接结算，这是阶段性简化。
后续关键词复杂起来后，会逐渐拆分出效果系统、战斗结算系统和死亡处理系统。
```

### 4. 第一个关键词：冲锋

面试表达：

```text
我先用冲锋验证了关键词系统的最小链路：
CardData 负责配置关键词，Minion 上场时复制关键词，GameManager 在召唤成功后判断是否有 Charge。
如果有冲锋，就把这个新随从的 CanAttack 设置为 true。
手牌 UI 通过 CardView 读取 CardData.Keywords，把 Charge 显示成“冲锋”。
这个机制没有急着上事件系统，因为冲锋只影响召唤后的攻击权限。
等做到亡语这种可能被多个来源触发的效果时，再引入 GameEventBus 会更自然。
```

### 5. 第二个关键词：嘲讽

面试表达：

```text
嘲讽和冲锋不同，它不是召唤时效果，而是攻击目标合法性规则。
所以我没有把它写进 Minion 自己，也没有让 UI 判断目标是否合法。
当前做法是在 GameManager 的攻击入口中统一判断：
攻击英雄前检查对方是否有活着的嘲讽随从；
攻击随从前检查如果对方有嘲讽，则目标必须也是嘲讽随从。
法术选目标不受嘲讽影响，这和炉石规则一致。
这仍然是阶段性简化，等圣盾、剧毒、风怒等攻击相关机制增加后，再把这些规则抽到 CombatResolver。
```

### 5.5 第五个关键词：圣盾

面试表达：

```text
圣盾和冲锋、嘲讽都不一样。
冲锋改变召唤后的攻击权限，嘲讽改变攻击目标是否合法，圣盾改变的是“受到伤害时的结果”。
当前阶段我先把圣盾放在 Minion.TakeDamage() 里：
如果随从有 DivineShield，并且受到正数伤害，就移除 DivineShield，然后本次实际伤害返回 0。
这样攻击和法术都会自然经过同一个 TakeDamage 入口，不需要在每个伤害来源里重复判断圣盾。
这是阶段性简化；后续如果出现免疫、法伤、吸血、伤害翻倍等更多伤害修改规则，就应该抽出 DamageResolver 或 CombatResolver。
```

### 6. 第一个战吼：对敌方英雄造成伤害

面试表达：

```text
战吼和冲锋、嘲讽不一样，它不是场上持续能力，而是打出时触发一次的效果。
所以我没有把 Battlecry 放进 KeywordType，而是单独做 BattlecryType 和 CardData 上的战吼配置。
当前最小战吼是：对敌方英雄造成固定伤害。
召唤随从成功后，GameManager 会进入 ResolveAfterSummon：
先处理召唤后关键词，例如冲锋；
再处理 ResolveBattlecry。
这一步还没有使用完整 GameEventBus，而是用普通方法模拟“发生召唤后触发效果”的思想。
之后我在亡语前引入了第一版事件系统，因为亡语会被攻击、法术、战吼和 AOE 等多个来源触发。
```

### 7. 第一版事件系统和第一个亡语

面试表达：

```text
我先做了 GameEventType、GameEvent 和 GameEventBus 三个类。
GameManager 在出牌、召唤和死亡时发布事件，调试日志可以监听这些事件。
做到亡语时，我没有让攻击流程或法术流程直接调用亡语，而是让 GameManager 监听 MinionDied。
这样无论随从是被攻击打死、被法术打死，还是未来被 AOE 或战吼打死，都可以走同一个死亡事件入口。
当前第一个亡语是：死亡后对敌方英雄造成固定伤害。
这还是阶段性简化；等亡语类型变多或出现亡语连锁时，会优先拆出 DeathProcessor 或 EffectSystem。
```

### 8. 使用 ScriptableObject 管理卡牌模板

面试表达：

```text
卡牌基础属性使用 ScriptableObject 配置，方便在 Unity Inspector 中创建和调整卡牌数据。
程序运行时会根据这些模板创建 Card 实例，避免直接修改模板。
```

### 9. 使用 Prefab 复用 UI

面试表达：

```text
手牌和战场都是重复元素，所以我用 CardViewPrefab 和 MinionViewPrefab 作为模板。
HandView 和 BoardView 根据运行时数据刷新 UI，已有 View 够用就复用，不够时才从 Prefab 创建。
这样既避免为每张牌手动摆对象，也减少了战斗中反复 Instantiate / Destroy 带来的 GC 和动画目标不稳定问题。
当前我没有引入完整对象池，因为 Demo 的手牌和随从数量很小；先做轻量复用更容易维护和讲清楚，后续有更复杂动画时再扩展成对象池。
```

### 10. 阶段 1.5 的 UI 反馈取舍

面试表达：

```text
阶段 1.5 我没有急着做完整美术，而是先解决原型展示最影响理解的问题：
费用不足、不能攻击、目标非法等操作会给出明确提示；
随从被选中时会高亮，玩家知道下一步要选择攻击目标。
这些反馈先放在 UI 层做轻量实现，没有引入正式事件系统或 ActionResult。
等阶段 2 做法术和关键词时，再把更复杂的结算和反馈接到事件驱动系统里。
```

### 11. 阶段 2 收尾复盘结论

面试表达：

```text
阶段 2 我没有追求大量卡牌，而是验证卡牌效果系统的几个核心形状：
法术验证“出牌后选择目标并造成伤害”；
冲锋、嘲讽和圣盾分别验证召唤后状态、攻击合法性和伤害结果修改；
战吼验证召唤后的即时效果；
亡语验证死亡事件触发效果。
这说明项目已经从最小战斗闭环扩展到了可继续扩展的规则骨架。
下一步做 AI 时，我会让 AI 先复用 GameActionGenerator 和 GameManager.ExecuteAction，最终仍落到现有详细规则入口，避免 AI 另写一套规则。
```

### 12. 战斗日志和动作执行闭环

面试表达：

```text
进入 AI 前，我补了两个关键工程点。
第一是 BattleLogger：伤害结算会记录尝试伤害和实际伤害，所以圣盾抵消时 UI 不再猜“造成了多少伤害”，而是显示 Core 的真实结算结果。
第二是 GameAction：玩家输入和 AI 都可以用同一种动作数据表达出牌、施法、攻击和结束回合。
GameActionGenerator 只枚举合法动作，不执行；GameManager.ExecuteAction 统一执行动作，并返回 GameActionResult。
这样 AI 第一版可以直接复用玩家规则，不需要另写一套出牌、嘲讽或攻击合法性判断。
```

### 13. AI 决策：合法动作、快照模拟和评估函数

面试表达：

```text
AI 没有直接操作手牌、战场或英雄血量，而是复用玩家同一套 GameActionGenerator 和 GameManager.ExecuteAction。
GameActionGenerator 只回答“当前有哪些合法动作”，不负责判断哪个动作更好。
ActionSelector 负责选择动作：先保留斩杀硬规则，其余动作会映射成 SnapshotAction，在 GameStateSnapshot 上模拟一步，再用 Evaluator 评分。
这样 AI 的“思考”发生在快照副本里，不会污染真实对局；最终执行仍然回到 GameManager.ExecuteAction，避免 AI 和玩家规则分叉。
```

可以强调的工程取舍：

```text
当前 AI 只搜索自己当前回合的少量后续动作，不做完整博弈树搜索。
这是阶段性简化：我先保证局面能被复制、动作能被模拟、评分能被解释，再逐步增加后续动作和搜索深度。
为了避免 AI 为了行动而行动，我先加了最小收益门槛；之后又加入了允许小亏阈值：除斩杀外，AI 可以接受小幅评分下降来换节奏，但超过阈值仍会结束回合。
这让 AI 行为既不会完全乱动，也不会因为一步评分略亏就过于保守。
```

当前已知局限：

```text
快照模拟还没有完整覆盖疲劳、玩家下一回合反击、多步连锁和亡语触发新的亡语连锁。
这不是最终 AI，而是求职 Demo 阶段的可解释 AI 骨架。
当前已经补了出随从关键词、两类无目标战吼、一层亡语伤害、具体手牌快照和英雄技能动作，后续可以继续补疲劳、多步连锁，并在 ActionSelector 上增加搜索深度。
```

### 14. 英雄技能闭环

面试表达：

```text
我没有把英雄技能写成 UI 的特殊逻辑，而是把它建模成 GameActionType.UseHeroSkillOnMinion 和 UseHeroSkillOnHero。
玩家点击按钮后进入选目标状态，最后仍调用 GameManager 的详细结果入口。
AI 也通过 GameActionGenerator 生成同样的英雄技能动作，再由 ActionSelector 和 ExecuteAction 执行。
这样英雄技能和出牌、攻击一样走统一规则入口，避免玩家和 AI 各写一套逻辑。
```

当前取舍：

```text
当前英雄技能固定为 2 费造成 1 点伤害，双方相同，没有职业差异、图标动画和复杂效果。
这是阶段性简化，目标是先验证资源消耗、每回合一次、目标选择、伤害结算和 AI 接入这条完整链路。
```

## 遇到的问题和解决

### NullReferenceException

问题：

```text
GameManager 开局时报 NullReferenceException。
调用链显示错误发生在 Card 构造函数中。
```

定位：

```text
Player 根据 Inspector 中的牌库列表创建 Card。
列表里有空的 CardData 槽位，导致 new Card(data) 时 data 为 null。
```

解决：

```text
在 Player 构造函数中检查 deckCards 和每个 CardData。
如果某个 CardData 是空的，就跳过。
同时在 Unity Inspector 中检查 Player Deck Data 和 Enemy Deck Data 是否有 None。
```

面试表达：

```text
这次问题让我意识到 Inspector 配置也需要防御性检查。
运行时代码不能默认所有编辑器配置都正确，所以我给 Player 创建牌库的流程加了空值保护。
```

### UI 可读性打磨

问题：

```text
第一版 UGUI 只是为了跑通功能，文字贴边、提示不明显，演示时不够容易读懂。
```

处理：

```text
我把视觉布局、字号、颜色和边距优先放在 Unity Editor / Prefab 中调整；
代码只负责刷新数据和控制运行时状态，例如选中高亮和操作提示内容。
```

面试表达：

```text
这是一次工程取舍：阶段 1.5 不做最终美术，但要让核心玩法和操作结果一眼可读。
我把 UI 布局留在 Prefab 里配置，避免把美术参数硬编码到逻辑脚本中。
```

## 当前可以演示的流程

演示顺序：

```text
1. 打开对战场景。
2. 展示 GameManager 上配置的卡牌数据。
3. Play 后展示手牌、法力、英雄血量。
4. 点击费用不足的手牌，展示非法操作提示。
5. 点击 1 费或 2 费手牌，召唤随从。
6. 点击火花，展示法术选目标；点击随从或英雄，展示 2 点伤害。
7. 展示手牌减少、法力减少、战场/英雄血量变化。
8. 点击 End Turn，展示当前行动者切换。
9. 双方各有随从后，点击己方 Ready 随从，展示选中高亮和提示。
10. 点击敌方随从，展示随从互相造成伤害。
11. 点击己方 Ready 随从，再点击敌方英雄，展示英雄血量减少。
12. 英雄血量归零后，展示 Game Over。
13. 给城墙守卫配置 Taunt 后，展示敌方有嘲讽时不能攻击英雄或非嘲讽随从。
14. 打出火焰学徒，展示手牌战吼文字，并展示敌方英雄立刻受到 1 点伤害。
15. 打出亡语炸弹人，展示手牌和场上亡语文字；让它死亡后展示敌方英雄受到 1 点伤害。
16. 打出圣盾卫士，展示手牌和场上“圣盾”；第一次受到伤害不掉血并失去圣盾，第二次正常掉血。
17. 点击英雄技能按钮并选择敌方随从或英雄，展示 2 费 1 点伤害、每回合一次和统一反馈。
```

讲解重点：

```text
每次 UI 操作都不是 UI 自己改状态，而是调用 GameManager。
状态变化发生在 Core，UI 只是刷新显示。
```

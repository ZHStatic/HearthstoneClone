## 一、范围界定：做什么，不做什么

### 要做（核心版 50-100 张卡）

- 随从卡：召唤、攻击、站位、关键词
- 法术卡：伤害、Buff、抽牌、召唤
- 武器卡（如时间允许）
- 5-10 个核心关键词（见阶段 2）
- 英雄技能
- 5 套预制主题套牌
- 单人 vs AI 对战
- 简易套牌选择/构筑界面
- 完整的主菜单 → 对战 → 结算流程

### 不做（留给未来或永远不做）

- 联网对战 / 服务器
- 天梯 / 竞技场 / 冒险模式
- 100+ 张卡牌
- 商店 / 充值 / 任务系统
- 自定义美术（全部用色块 + 免费素材）

### 面试官 5 分钟看什么

| 加分项 | 不重要 |
|--------|--------|
| ✅ 代码架构清晰可扩展 | ❌ 卡牌数量多 |
| ✅ 核心玩法完整流畅 | ❌ 有联网对战 |
| ✅ 效果系统能处理复杂交互 | ❌ 美术精美 |
| ✅ UI 专业可交互 | ❌ 项目大而全 |
| ✅ Git 提交历史规范 | ❌ — |

## 二点五、求职导向优先级

从中国游戏行业求职角度看，后续重点从“继续加复杂规则”转向“商业项目完成度”：

```text
1. 英雄技能最小闭环
2. 战斗 / UI 状态重新梳理
3. UI 视觉和交互大改
4. 出牌 / 攻击 / 受伤 / 死亡动画
5. 主菜单 -> 选套牌 -> 对战 -> 结算
6. 移动端 / 性能意识补强
7. 数据配置和测试工具补强
8. README、演示视频、面试讲稿
```

优先级理由：

| 方向 | 为什么重要 |
|------|------------|
| 英雄技能 | 补齐炉石类核心对局体验，让项目不像“随从 + 法术原型” |
| UI / 交互 / 反馈 | 面试官第一眼看到的是画面、操作反馈和完成度 |
| 表现层动画和音效 | 让出牌、攻击、受伤、死亡有游戏节奏，而不是纯规则验证 |
| 主流程闭环 | 从主菜单到结算才像可交付 Demo |
| 移动端 / 性能意识 | 国内 Unity 岗位常问 UI 重建、GC、对象创建、资源和分辨率适配 |
| 数据配置和工具化 | 展示“程序支持策划配置内容”的行业协作意识 |
| 求职包装 | 把技术点转化成面试官能快速理解的作品材料 |

后续原则：规则系统保持可讲，AI 保持可玩，UI 做到第一眼像游戏。

## 三、核心架构

### 事件驱动的效果结算系统

```
                    ┌─────────────┐
                    │  GameEvent  │  ← 任何"发生的事"
                    │  (事件中心)  │
                    └──────┬──────┘
                           │ 广播事件
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ 卡牌效果  │ │ 关键词   │ │ UI 更新  │
        │ 监听器    │ │ 监听器   │ │ 监听器   │
        └──────────┘ └──────────┘ └──────────┘
```

**为什么用事件系统？** 炉石的效果是连锁触发的——一个亡语触发另一个亡语、法伤加成影响 AOE。如果用"直接调方法"，代码会散落在几十个文件里。事件系统让每个效果只管自己的监听，互不干扰。

### 目录结构

```
Assets/Scripts/
├── Core/                    # 纯逻辑，不依赖 Unity UI
│   ├── GameManager.cs       # 游戏总控（当前阶段的规则调度入口）
│   ├── Cards/               # 卡牌模板、运行时卡牌和卡牌类型
│   ├── Entities/            # 英雄、玩家、随从、战场
│   ├── Actions/             # 动作数据、动作结果、合法动作生成
│   ├── Effects/             # 关键词、战吼、亡语、法术目标类型
│   ├── Events/              # 事件系统
│   └── Logging/             # 战斗日志和伤害记录 helper

├── AI/                      # AI 系统
│   ├── AIController.cs      # AI 入口
│   ├── ActionSelector.cs    # 从合法动作中选择一个动作
│   ├── AIActionSelection.cs # AI 选择结果：动作 + 原因
│   ├── AIActionSelectionReason.cs # AI 选择原因枚举
│   ├── Evaluator.cs         # 局面评估函数
│   ├── EvaluationResult.cs  # 评分明细
│   └── Simulation/          # 快照数据、动作映射和单步模拟

└── UI/                      # 界面
    ├── Controllers/         # UI 总控和输入流程
    ├── Views/               # 手牌、场面、卡牌、随从视图
    └── Formatters/          # UI 文本格式化工具
```

### 阶段 3：AI 对手（4-6 周）

**不搞深度学习。用博弈树搜索 + 评估函数。**

当前阶段 3 已完成基础链路、评估模拟入口、评分优先级选择、保守度调校入口、出随从模拟补强、亡语伤害模拟、同回合后续攻击预估、具体手牌快照和继续出牌模拟。阶段 3.13 英雄技能最小闭环正在进行，Core 规则、动作系统和 AI 快照链路已写入，玩家 UI 交互和 Play 模式验证尚未完成：

```text
GameActionGenerator 枚举合法动作
-> ActionSelector 选择动作并记录原因
-> AIController 调用 GameManager.ExecuteAction(action)
-> Console 输出 AI 行动、理由和结果
-> Evaluator 输出真实局面和快照局面评分
-> SnapshotSimulator 模拟合法动作后的局面
-> ActionSelector 按模拟评分选择动作，并允许小幅亏分换节奏
-> 出随从模拟会考虑关键词和当前两类无目标战吼
-> 死亡模拟会处理一层“对敌方英雄造成伤害”的亡语
-> 候选动作评分会粗略预估最多 2 次同回合后续随从攻击
-> PlayerSnapshot 会保存具体 CardSnapshot 手牌数据
-> SnapshotFollowUpEvaluator 会基于 CardSnapshot 继续模拟出牌和攻击
-> 英雄技能动作已进入合法动作生成、统一执行入口、快照映射、快照模拟和 AI 选择日志
```

当前 AI 仍是阶段性简化：已经能评分、单步模拟、少量同回合后续攻击预估，并能在快照中记录和继续使用具体手牌；`ActionSelector` 已接入评分优先级和允许小亏阈值；快照模拟已覆盖出随从关键词、当前两类无目标战吼、一层亡语伤害和第一版英雄技能伤害。当前只搜索己方同回合后续动作，还没有做对手回合 Minimax。

```
AI 决策流程：

1. 枚举所有合法操作
   ├── 能出的牌（费用够 + 目标合法）
   ├── 能攻击的随从（己方随从 → 敌方目标）
   ├── 英雄技能（费用够）
   └── 结束回合（永远可选）

2. 模拟每种选择的结果（深度 2-3 步）

3. 评估函数打分：
   ├── 场面优势 = 己方随从总属性 - 敌方随从总属性
   ├── 血量差
   ├── 卡差 = 手牌数量差
   └── 节奏 = 是否有效利用法力水晶

4. 选最高分 → 执行
```

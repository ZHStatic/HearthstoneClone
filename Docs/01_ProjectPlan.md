# HearthstoneClone 项目开发计划

> 本文只记录长期计划、阶段目标和范围边界；实际进度、验证结果和当前停靠点只维护在 `Docs/00_CurrentStatus.md`。

---

## 项目定位

单人版炉石传说核心对战体验 | Unity 2D Built-In RP | 求职 Demo

**目标岗位：** Unity 游戏开发 / 策划

**核心原则：** 精致的核心体验 > 粗糙的大而全

面试官 5 分钟内应该能看懂：

- 对局流程完整：抽牌、出牌、攻击、技能、结束回合、胜负。
- 架构边界清楚：Core 负责规则，UI 负责展示和输入，AI 复用 Core 动作系统。
- 规则扩展有思路：关键词、战吼、亡语、英雄技能和战斗日志都能继续扩展。
- Demo 完成度够高：操作反馈、视觉层级、动画和主流程能支撑演示。

## 个人约束

| 维度 | 情况 |
|------|------|
| 编程基础 | 基础不多，无游戏开发经验 |
| Unity 水平 | 只会基本操作 |
| 可用时间 | 周内晚上 1-2h + 周末 2-10h（约 10-20h/周） |
| 学习方式 | 项目驱动，边做边学，不提前系统学完再动手 |

计划安排要服务这几个约束：

- 每个阶段切成能提交的小功能。
- 优先做能演示、能解释、能形成作品材料的内容。
- 阶段性简化必须能说清楚取舍，不追求一次做成商业项目终版。

## 范围界定

### 要做

- 随从卡：召唤、攻击、站位、关键词。
- 法术卡：伤害、Buff、抽牌、召唤。
- 英雄技能：先做通用技能，再考虑职业差异。
- 5-10 个核心关键词或效果机制。
- 5 套预制主题套牌。
- 单人 vs AI 对战。
- 主菜单、套牌选择、对战、结算流程。
- 基础动画、音效、战斗反馈和演示包装。

### 不做

- 联网对战 / 服务器。
- 天梯 / 竞技场 / 冒险模式。
- 商店 / 充值 / 任务系统。
- 大规模卡牌池，目标控制在 50-100 张以内。
- 自定义高成本美术，优先使用色块、免费素材和简洁 UI。

## 求职导向优先级

后续投入优先从“继续加复杂规则”转向“商业项目完成度”：

1. UI / 交互 / 表现打磨。
2. 出牌、攻击、受伤、死亡、回合切换动画。
3. 主菜单 -> 选套牌 -> 对战 -> 结算。
4. 移动端 / 性能意识补强。
5. 数据配置和测试工具补强。
6. README、演示视频、面试讲稿。

| 方向 | 为什么重要 |
|------|------------|
| UI / 交互 / 反馈 | 面试官第一眼看到的是画面、操作反馈和完成度 |
| 表现层动画和音效 | 让出牌、攻击、受伤、死亡有游戏节奏，而不是纯规则验证 |
| 主流程闭环 | 从主菜单到结算才像可交付 Demo |
| 移动端 / 性能意识 | 国内 Unity 岗位常问 UI 重建、GC、对象创建、资源和分辨率适配 |
| 数据配置和工具化 | 展示“程序支持策划配置内容”的行业协作意识 |
| 求职包装 | 把技术点转化成面试官能快速理解的作品材料 |

## 架构方向

### 核心边界

- Core 层只负责规则、状态和结算，不依赖 UI。
- UI 层读取 Core 状态，把玩家输入转换成 `GameManager` / `GameAction` 调用。
- AI 层通过合法动作生成和统一执行入口行动，不直接修改游戏状态。
- 数据配置优先使用 ScriptableObject，方便后续做卡牌和套牌内容。

### 规则系统方向

事件系统用于处理真正需要“发生后触发”的规则，例如死亡事件和亡语。

```text
游戏行为
-> Core 规则结算
-> 必要时发布事件
-> 效果监听事件并结算
-> 记录战斗日志
-> UI 读取结果刷新显示
```

当前阶段可以保留部分直接结算的阶段性简化，例如简单法术、基础战吼和英雄技能；如果后续出现大量连锁、替换、免疫、法伤、吸血等机制，再考虑抽出更完整的 `CombatResolver` / `DamageResolver` / `EffectResolver`。

### 目录规划

```text
Assets/Scripts/
├── Core/                    # 规则和状态，不依赖 Unity UI
│   ├── Cards/               # 卡牌模板、运行时卡牌和卡牌类型
│   ├── Entities/            # 英雄、玩家、随从、战场
│   ├── Actions/             # 动作数据、动作结果、合法动作生成
│   ├── Effects/             # 关键词、战吼、亡语、法术目标类型
│   ├── Events/              # 事件系统
│   └── Logging/             # 战斗日志和伤害记录
├── AI/                      # AI 行动、评分和快照模拟
└── UI/                      # 界面控制器、视图和文本格式化
```

## 阶段目标

### 阶段 1：最小可玩原型

目标：用最简单的界面跑通一局对战。

- 卡牌数据结构：名称、费用、攻击、生命。
- 手牌和牌库：抽牌、显示手牌。
- 出牌：点击手牌召唤随从。
- 随从攻击：己方随从攻击随从或英雄。
- 法力水晶：每回合增长和消耗。
- 回合流程：抽牌、行动、结束回合。
- 胜负判定：英雄生命归零。

刻意不做：法术牌、关键词、AI、动画和复杂 UI。

### 阶段 1.5：原型展示打磨

目标：让最小闭环更容易测试、展示和讲解。

- 补基础随从卡，覆盖低费、中费、高费。
- 增加选中反馈和非法操作提示。
- 整理演示步骤和 README 说明。
- 检查文档、Git 提交历史和场景引用。

### 阶段 2：法术牌与关键词系统

目标：让项目从“随从互打”升级为有规则扩展能力的卡牌对战。

- 卡牌类型区分随从和法术。
- 单目标伤害法术。
- 关键词顺序：冲锋、嘲讽、圣盾。
- 一次性效果：战吼。
- 死亡触发效果：亡语。
- 规则结算结果能反馈给 UI。
- 战斗日志记录关键结算。

验收标准：

- 玩家能使用随从、法术和关键词卡牌完成对局。
- UI 显示的伤害和反馈来自 Core 实际结果，不自己猜。
- 新增简单效果时，不需要大面积修改 UI。

### 阶段 2.10：进入 AI 前的结构整理

目标：为 AI 复用玩家规则打基础。

- `GameActionResult`：Core 返回成功、失败原因和反馈文本。
- Player 状态封装：外部不能直接改手牌和牌库。
- `GameAction`：用统一数据描述出牌、施法、攻击、英雄技能和结束回合。
- `GameActionGenerator`：只生成合法动作，不做决策。
- `GameManager.ExecuteAction()`：玩家和 AI 共用执行入口。

### 阶段 3：AI 对手

目标：做一个可对战、可解释、可调试的 AI。

- 枚举合法动作：出牌、施法、攻击、英雄技能、结束回合。
- 第一版动作选择：斩杀、解场、出牌、兜底。
- 评估函数：英雄血量、手牌、场面。
- 快照模拟：脱离真实局面试算动作结果。
- 同回合后续预估：减少单步评分短视。
- AI 日志：输出选择动作、原因和评分变化。

阶段性简化：

- 不做深度学习。
- 不追求完整 Minimax。
- 先搜索己方同回合短链路，后续再考虑对手回合。

### 阶段 3.13：英雄技能最小闭环

目标：补齐炉石类对局的核心体验，但不做复杂职业系统。

- 英雄技能按钮：2 费，每回合一次。
- 第一版技能：对敌方英雄或敌方随从造成 1 点伤害。
- 使用技能后刷新法力、按钮状态和反馈文本。
- 英雄技能接入 `GameAction` / `GameActionGenerator` / `ExecuteAction`。
- AI 能把英雄技能用于斩杀、补刀或补伤害。
- 快照模拟和评分能理解英雄技能。

阶段性简化：

- 先不做多职业英雄技能。
- 先不做英雄技能动画，只保留按钮状态和操作反馈。
- 先不做英雄头像、职业皮肤和技能图标资源。

### 阶段 4：UI / 交互 / 表现打磨

目标：让项目第一眼看起来像一款可展示的卡牌游戏，而不是规则验证工具。

- 战斗界面重新布局：英雄区、手牌区、双方战场、法力、回合按钮、反馈文本。
- 手牌卡牌视觉重做：费用、名称、攻击、生命、关键词、战吼和亡语描述。
- 场上随从视觉重做：攻击、生命、关键词、是否可攻击、选中状态。
- 合法目标反馈：攻击、法术、英雄技能选择目标时，合法目标更明显。
- 按钮状态：结束回合、英雄技能、可交互区域状态清晰。
- 最近行动反馈：出牌、伤害、圣盾抵消、亡语、胜负。
- 基础动画：出牌、召唤、攻击、受伤、死亡、回合切换。
- 基础音效：按钮、出牌、攻击、受伤、胜负。

Unity 协作边界：

- 视觉布局、字号、颜色、边距、图片资源优先在 Unity Editor / Prefab 中调整。
- 运行时状态、交互反馈、合法目标判断、按钮可用状态由代码控制。
- Codex 默认不直接改 Scene、Prefab、ScriptableObject 和 `.meta`，需要改时先确认风险。

### 阶段 4.5：主流程与套牌选择

目标：从“单场战斗 Demo”升级为“有入口、有选择、有结算”的完整体验。

- 主菜单：开始游戏、退出、项目说明入口。
- 套牌选择：至少 3 套预制套牌，最终目标 5 套。
- 套牌主题：快攻、嘲讽防守、亡语、法术伤害、均衡。
- 对战开始时根据选择加载玩家套牌和 AI 套牌。
- 胜负结算界面：显示胜利 / 失败、回到主菜单、再来一局。
- 演示模式：一键进入稳定测试局面，方便录屏和面试演示。

### 阶段 4.8：移动端 / 性能意识补强

目标：不追求商业上线级优化，但要能展示 Unity 客户端常见性能意识。

- 检查 UI 刷新，减少全量销毁和重建 View。
- 手牌和随从 View 复用，必要时引入简单对象池。
- 避免战斗中频繁 `Instantiate` / `Destroy`。
- 检查战斗热路径里的 GC Alloc，例如字符串拼接、临时 List、频繁 LINQ。
- 适配常见屏幕比例，至少检查 16:9 和 19.5:9。
- 整理性能说明：做了什么、没做什么、为什么当前阶段这样取舍。

### 阶段 5：数据配置和测试工具补强

目标：展示商业项目里“程序支持策划配置和验证内容”的意识。

- 卡牌数据检查工具：空名称、负费用、随从血量非法、法术缺少目标等。
- 测试套牌工具：一键应用不同主题牌组。
- 卡牌列表导出：生成便于 README 或面试展示的卡牌清单。
- 调试开关整理：集中记录 AI、洗牌、日志等入口。
- 关键回归清单：出牌、攻击、法术、战吼、亡语、圣盾、英雄技能、AI。

### 阶段 6：求职包装

目标：把项目成果转化成面试官能快速理解的作品材料。

- 录制 2-3 分钟玩法演示视频。
- 完善 README 和仓库描述。
- 补充截图、GIF 或短视频链接。
- 写技术博客：动作系统、快照模拟、事件结算、UI 打磨取舍。
- 准备 5 分钟面试讲稿：项目目标、架构亮点、难点、取舍、后续优化。
- 确认 commit 历史干净规范。

## Git 提交规范

```text
feat: 新功能        -> feat: 实现法力水晶系统
fix: 修 bug         -> fix: 修复随从死亡后仍能攻击
refactor: 重构      -> refactor: 提取攻击结算为独立方法
chore: 杂项配置     -> chore: 更新 .gitignore
docs: 文档更新      -> docs: 补充架构说明
```

原则：

- 每完成一个小功能 commit 一次。
- commit message 可以使用中文。
- Scene / Prefab / ScriptableObject 等 Unity 资源改动要确认来自 Unity Editor，避免手改 GUID 和引用。

## AI 协作原则

> 每行代码都必须自己读懂。

协作时始终问三个问题：

1. 这个类负责什么？
2. 它依赖谁？
3. 谁依赖它？

遇到不懂的语法、Unity 概念或工程取舍，优先追问并补学习笔记，不把不理解的代码继续往下堆。

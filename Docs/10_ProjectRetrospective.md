# Project Retrospective

最后更新：2026-07-08

## 结论

本项目从现在开始停止继续扩展功能，进入复盘和作品包装阶段。

原因不是项目失败，而是它已经完成了第一个 Unity 卡牌对战 Demo 最重要的学习目标：

- 跑通了抽牌、出牌、攻击、法术、关键词、英雄技能、回合、胜负和 AI 对手。
- 验证了 `CardData` / `DeckData` / `GameAction` / `GameActionGenerator` / `ExecuteAction()` 等关键工程概念。
- 通过 UI 高亮、反馈文本、基础音效、套牌选择和演示模式，把项目从规则验证推进到了可演示状态。

继续在当前结构上增加阶段 5 数据工具或更多卡牌机制，学习收益会下降。更有价值的下一步是保留它作为第一个完整 Demo，整理可展示材料，并把架构问题转化成下一个小项目的设计目标。

## 项目保留价值

这个项目适合作为“第一个完整 Unity 作品”保留，而不是作为长期维护的复杂卡牌框架继续扩展。

可以展示的价值：

- 完整对局闭环：玩家可以完成一局单人卡牌对战。
- 规则扩展意识：冲锋、嘲讽、圣盾、战吼、亡语和英雄技能分别覆盖了不同规则触发点。
- Core / UI 基础分层：UI 不直接改手牌、法力、战场和英雄生命，而是调用 Core 规则入口。
- AI 工程尝试：AI 通过合法动作、快照模拟和评分函数行动，而不是硬编码固定脚本。
- Unity 客户端意识：使用 ScriptableObject、Prefab、UGUI、View 复用、基础表现和横屏比例检查。

面试时可以诚实说明：这是第一个项目，重点是完整流程和工程意识；它不是商业级架构终版。

## 主要妥协

### `GameManager` 过重

当前 `GameManager` 承担了开局、回合、出牌、攻击、法术、战吼、亡语触发、英雄技能、死亡清理、胜负判断和调试入口。

这是阶段性简化。早期能快速跑通闭环，但后期继续加入更多效果时，会让规则入口越来越拥挤。

如果重做，应优先拆出：

- `TurnController`：回合切换、抽牌、法力刷新。
- `ActionExecutor`：统一执行玩家和 AI 动作。
- `CombatResolver` / `DamageResolver`：攻击和伤害结果修改。
- `EffectResolver`：战吼、亡语、法术和英雄技能效果。

### 效果系统没有统一

当前法术、战吼、亡语和英雄技能都能跑通，但实现形态不统一：

- 简单法术由 `GameManager` 直接结算。
- 战吼在召唤后直接调用。
- 亡语通过 `MinionDied` 事件触发。
- 英雄技能通过动作系统接入，但具体效果仍是固定伤害。

这个取舍适合学习不同触发点，但不适合继续扩展大量卡牌。成熟项目会把“效果描述”和“效果执行”拆得更清楚，让卡牌数据驱动效果解析。

### UI 是后补打磨，不是从状态流设计

项目早期 UI 主要服务于验证规则，后期逐步补了反馈文本、目标高亮、按钮状态、表现控制器和套牌选择。

这让 Demo 可用，但 `GameUIController` 也承担了较多输入状态和刷新协调职责。

如果重做，应先定义 UI 状态机，例如：

- 空闲状态。
- 选择攻击目标。
- 选择法术目标。
- 选择英雄技能目标。
- 对局结束状态。

然后让 UI View 只根据状态渲染，而不是在控制器里不断追加分支。

### AI 快照模拟和真实规则有重复

AI 的快照模拟是本项目的亮点之一，但它也暴露了成本：真实规则每补一个效果，快照层也要补一份近似模拟。

这说明当前架构还没有做到“同一套规则既能真实执行，也能在副本上模拟”。在求职 Demo 里可以接受，因为它清楚展示了 AI 思路；但如果要继续做复杂 AI，应考虑让规则执行器支持传入不同状态容器，减少真实规则和模拟规则分叉。

### 缺少自动化测试

当前验证主要依赖 Unity Play 模式和文档回归清单。对第一个 Unity 项目来说可以接受，但它限制了继续重构的信心。

如果重做，应从很小的 Core 测试开始：

- 费用不足不能出牌。
- 嘲讽限制攻击目标。
- 圣盾抵消第一次正数伤害。
- 亡语在死亡后触发。
- 英雄技能每回合只能使用一次。

这些测试不需要 UI，也不应该依赖场景。

## 学到的关键经验

### 先跑通闭环是对的

如果一开始就设计完整效果系统、AI 搜索和 UI 状态机，很容易卡在抽象上。这个项目先做出可玩闭环，让很多工程问题变得具体，这是正确的学习路径。

### 妥协要及时收口

阶段性简化本身不是问题，问题是继续在简化结构上叠加大量新功能。当前停止功能扩展，就是一次正确的收口。

### 文档不是补救，而是学习资产

`Docs/02_CoreArchitecture.md`、`Docs/03_UIArchitecture.md`、`Docs/08_AIReview.md` 和 `Docs/09_PerformanceMobileReview.md` 已经把很多取舍记录下来。它们让这个项目即使不继续开发，也能作为面试讲解材料。

## 面试表达

可以这样讲：

```text
这是我的第一个 Unity 卡牌对战项目。我先用它完成了从规则、UI、AI 到主流程的完整闭环。
项目里有一些架构妥协，例如 GameManager 偏重、效果系统不统一、AI 快照和真实规则存在重复。
这些问题不是我打算掩盖的部分，反而是这个项目给我的主要收获：我通过实际迭代理解了为什么要拆 ActionExecutor、EffectResolver、DamageResolver 和 UI 状态机。
所以我把它停在可演示状态，后续如果做第二版，会用更小范围专门验证清晰架构，而不是继续在旧结构上堆功能。
```

不要把项目包装成商业级炉石框架。更好的定位是：

```text
一个完整的 Unity 卡牌对战学习项目，展示了核心玩法闭环、规则扩展尝试、AI 决策雏形，以及对架构取舍的复盘能力。
```

## 包装清单

后续只做包装，不继续加功能：

- README 改成“当前功能冻结，进入复盘和包装”口径。
- 准备 2-3 分钟演示视频：套牌选择 -> 演示模式 -> 出牌 / 法术 / 攻击 / 英雄技能 -> AI 行动 -> 结算。
- 截图 4 张：套牌选择、对战界面、目标高亮、结算界面。
- 整理 5 分钟面试讲稿：目标、完成度、核心架构、AI 思路、架构不足、如果重做会怎么设计。
- 不再新增 C# 规则功能，除非是为了修复影响演示的明确 bug。

## 下一个项目建议

下一个练架构的项目不建议重做完整炉石。

更合适的是做一个小型 `CardBattleCoreV2`：

- 无 Unity UI 或只有极简 Console / 测试入口。
- 只做 10 张卡以内。
- 重点练动作执行器、效果解析器、伤害结算器和自动化测试。
- 所有规则优先用单元测试验证，再考虑 Unity 表现。

目标不是“更大”，而是“边界更清楚”。

AI Simulation 模块看板

目标：让 AI 在"做决定之前"预览每个候选动作后的局面，选最好的执行，且预览过程完全不碰真实游戏状态。

0. 概述

当前 AI 系统分为两大块：

块职责一句话
决策层 AIController / ActionSelector / Evaluator "现在能做什么？选哪个？"
模拟层 GameStateSnapshot / SnapshotActionMapper / SnapshotSimulator "如果选这个，会变成什么样？"

模拟层是这篇文章的主角。它做的是 AI 的"脑内推演"——像下棋时在脑子里想"如果走这一步，会怎样"。

核心设计思想（四个）

① 快照模式 (Snapshot Pattern) — 拍照而不是改原件
② 不可变拷贝 (Immutable Copy) — 每次修改都创建新对象，旧对象永不被污染
③ 轻量化 (Lightweight) — 只抄 AI 评估需要的数据，其余全扔
④ 索引代替引用 (Index over Reference) — 快照世界里没有真实对象，用"第几个"来定位

2. AI 决策完整时间线

从"轮到 Enemy"到"AI 执行完一个动作"的全流程。

1
轮到敌方回合
GameManager.EndTurn() → StartTurn(enemy)
敌方补法力、抽牌。CurrentPlayer 切换为 Enemy。
2
AI 接管
AIController.TakeTurn()
开始循环：生成动作 → 选择 → 执行，直到选了 EndTurn 或达到上限。
3
枚举合法动作
GameActionGenerator.GenerateLegalActions(gameManager)
扫描手牌（费用够不够）、场上随从（能不能攻击）、英雄技能等，生成合法动作列表。
例如：[打出石牙野猪, 野猪攻击敌方英雄, 野猪攻击嘲讽龟, 结束回合]
4
选择动作
ActionSelector.SelectAction(legalActions)
当前策略（规则优先级）：
① 能斩杀英雄 → 选它
② 能击杀敌方随从 → 选威胁最大的
③ 有可出手牌 → 选费用最高的
④ 兜底 → 按固定优先级（攻英雄 > 攻随从 > 出随从 > 结束回合）

未来策略（评分驱动）：对每个候选动作做快照模拟 → 评分 → 选分最高的。
5
【可选】快照模拟 + 评分（当前仅用于日志对比）
GameStateSnapshot.FromGameManager() → SnapshotSimulator.Simulate() → Evaluator.Evaluate()
这是 Simulation 模块登场的位置。目前主要用于验证"快照评分和真实评分是否一致"，不参与实际决策。
6
执行动作
GameManager.ExecuteAction(selectedAction)
统一执行入口。分发到具体的 Try...Detailed 方法。
7
记录日志
AIController 拼接单行日志输出到 Console
格式：AI 行动：xxx | 理由：xxx | 评分：xxx → xxx | 结果：xxx
8
循环或结束
如果执行的是 EndTurn → 退出循环。否则回到步骤 3 继续生成动作（因为局面变了）。

3. Simulation 三层拆解

3.1 数据层 — 快照对象

这四个类的共同特点：只存数据，没有行为方法。所有属性 private set，创建后不可修改（Immutable）。

GameStateSnapshot — 整局快照的"根"

// 文件：Assets/Scripts/AI/Simulation/GameStateSnapshot.cs

public class GameStateSnapshot
{
    public const int PlayerIndex = 0;   // 用 0/1 代替真实 Player 引用
    public const int EnemyIndex  = 1;

    public int CurrentPlayerIndex;        // 当前是谁的回合（0 或 1）
    public PlayerSnapshot Player;           // 玩家状态
    public PlayerSnapshot Enemy;            // 敌方状态
    public BoardSnapshot Board;             // 双方战场
}
方法用途
FromGameManager(GameManager)工厂方法：从真实对局拍一张快照
GetCurrentPlayer()返回当前回合玩家的 PlayerSnapshot
GetOpponentPlayer()返回对手的 PlayerSnapshot

PlayerSnapshot — 玩家状态的 6 个 int

public class PlayerSnapshot
{
    // 6 个字段，全部是 int。没有 Hero 引用，没有 Card 列表。
    public int HeroHealth;      // 当前血量
    public int HeroMaxHealth;   // 最大血量
    public int CurrentMana;     // 当前剩余法力
    public int MaxMana;         // 最大法力水晶
    public int HandCount;       // 手牌数量（不知道是什么牌！）
    public int DeckCount;       // 牌库数量
}
为什么丢弃具体手牌信息？
当前评估只看"有几张牌"，不看"是什么牌"。评估公式是 手牌数差 × 4。
如果以后要评估手牌质量（比如手里有 AOE），就需要扩展快照，记录每张牌的 CardData 引用或摘要。

MinionSnapshot — 随从状态的 7 个字段

public class MinionSnapshot
{
    // 7 个字段。没有 CardData 引用，没有 Owner 引用，没有战吼/亡语效果。
    public int  Attack;
    public int  CurrentHealth;
    public int  MaxHealth;
    public bool CanAttack;           // 本回合是否能攻击
    public bool HasTaunt;            // 是否有嘲讽
    public bool HasDivineShield;     // 是否有圣盾
    public bool HasCharge;           // 是否有冲锋
}

BoardSnapshot — 双方随从列表

public class BoardSnapshot
{
    private readonly List<MinionSnapshot> playerMinions;  // 己方随从
    private readonly List<MinionSnapshot> enemyMinions;   // 敌方随从

    // 对外只暴露 IReadOnlyList，外部不能 Add/Remove
    public IReadOnlyList<MinionSnapshot> PlayerMinions;
    public IReadOnlyList<MinionSnapshot> EnemyMinions;
}
BoardSnapshot 构造器里的 CopyMinions 在干什么？
这是防御性拷贝——构造器收到外部传入的 List 后，不直接存引用，而是复制一份。
这样外部后续修改它自己的 List（比如 Clear），不会污染 BoardSnapshot 内部的数据。
类比：收到一份名单，自己抄一份存档，别人事后在他的名单上乱画，不影响你的存档。

3.2 映射层 — SnapshotActionMapper

职责：把真实 GameAction（包含 Minion/Card/Hero 引用）翻译成 SnapshotAction（只有索引和数值）。

  输入（真实世界）                         输出（快照世界）

  GameAction                               SnapshotAction
  ├ ActionType: AttackMinion               ├ ActionType: AttackMinion
  ├ Attacker: <Minion对象引用>      →      ├ AttackerIndex: 2  (己方列表第3个)
  ├ TargetMinion: <Minion对象引用>  →      ├ TargetMinionIndex: 0 (对方列表第1个)
  ├ Actor: <Player对象引用>         →      ├ ActorIndex: 1 (Enemy)
  └ (没有数值字段)                          ├ CardCost: 0
                                            ├ CardAttack: 0
                                            └ SpellDamage: 0

核心翻译过程（以攻击为例）：

// SnapshotActionMapper.TryMapAttackMinion
int attackerIndex = FindMinionIndex(board, actor, action.Attacker);
// ↑ 在真实己方场面里找到"攻击者"是第几个随从 → 比如第3个，索引就是2

int targetIndex = FindMinionIndex(board, opponent, action.TargetMinion);
// ↑ 在真实对方场面里找到"目标"是第几个随从 → 比如第1个，索引就是0

return SnapshotAction.CreateAttackMinion(actorIndex: 1, attackerIndex: 2, targetIndex: 0);
// ↑ 构造一个只有索引的快照动作
TryMap 能翻译哪些动作当前不能翻译的
PlayMinionCard（费用/攻击/血量）
PlaySpellOnMinion（费用/伤害/目标索引）
PlaySpellOnHero（费用/伤害）
AttackMinion（攻击者索引/目标索引）
AttackHero（攻击者索引）
EndTurn 		友方目标法术（当前只支持敌方目标）
治疗、Buff、AOE
战吼、亡语（快照目前不模拟）
找不到索引的动作（返回 false）

3.3 执行层 — SnapshotSimulator

职责：输入旧快照 + 快照动作 → 输出新快照。不修改输入。

public static class SnapshotSimulator   // ← 全静态类，纯工具箱
{
    public static GameStateSnapshot Simulate(
        GameStateSnapshot state,
        SnapshotAction action)
    {
        // 第一步：把 state 里的所有东西深复制一份
        PlayerSnapshot player = CopyPlayer(state.Player);
        PlayerSnapshot enemy  = CopyPlayer(state.Enemy);
        List<MinionSnapshot> players = CopyMinions(state.Board.PlayerMinions);
        List<MinionSnapshot> enemies = CopyMinions(state.Board.EnemyMinions);

        // 第二步：在副本上执行动作（用 switch 分发到具体模拟方法）

        // 第三步：用修改后的副本构造新快照返回
        return new GameStateSnapshot(currentPlayer, player, enemy,
                                new BoardSnapshot(players, enemies));
    }
    // 旧的 state 完好无损！可以继续用于模拟下一个候选动作。
}

每个"修改"方法都遵循不修改输入，返回新对象的规则：

// 扣血方法：不改旧 minion，创建新的返回
private static MinionSnapshot DamageMinion(MinionSnapshot minion, int damage)
{
    if (damage <= 0) return minion;                // 没伤害就不变

    if (minion.HasDivineShield)                   // 有圣盾 → 抵消伤害，移除圣盾
        return new MinionSnapshot(attack, hp, hp, canAttack,
                                hasTaunt, false, hasCharge);

    return new MinionSnapshot(attack, hp - damage, hp, ...);
    //                           ↑ 只有血量变了，其余字段原样复制
}
当前模拟什么 / 不模拟什么：
✅ 伤害、死亡移除、圣盾抵消、费用消耗、手牌数-1、不能再次攻击
❌ 战吼效果、亡语效果、冲锋（新随从默认不能攻击）、嘲讽限制（攻击时不检查）、友方法术目标

4. 走读实例

假设当前局面，AI 持有法术"火花"（2费造成3点伤害），候选动作是"对敌方嘲讽龟释放火花"。下面完整走一遍快照模拟流程：

  初始真实局面：
    玩家英雄 30血，场上 [3/2 野猪]
    敌方英雄 28血，场上 [2/3 嘲讽龟]（嘲讽、圣盾）
    AI 手牌："火花" (2费 造成3伤)
    AI 法力：4

  ═══════════════════════════════════════════════════════════════

  Step 1：拍快照
  GameStateSnapshot.FromGameManager(gameManager)
    → GameStateSnapshot {
        CurrentPlayerIndex: 1 (Enemy),
        Player:  PlayerSnapshot { HeroHealth:30, HandCount:..., ... },
        Enemy:   PlayerSnapshot { HeroHealth:28, CurrentMana:4, HandCount:3, ... },
        Board:   BoardSnapshot {
          PlayerMinions: [ MinionSnapshot{Attack:3, HP:2, CanAttack:true, ...} ],
          EnemyMinions:  [ MinionSnapshot{Attack:2, HP:3, HasTaunt:true, HasDivineShield:true} ]
        }
      }

  Step 2：映射动作
  SnapshotActionMapper.TryMap(火花打嘲讽龟的GameAction, ...)
    → 找到敌方Index=1，嘲讽龟在敌方场面索引=0
    → SnapshotAction {
        ActionType: PlaySpellOnMinion,
        ActorIndex: 1 (Enemy),
        CardCost: 2,
        SpellDamage: 3,
        TargetMinionIndex: 0
      }

  Step 3：模拟执行
  SnapshotSimulator.Simulate(快照, 快照动作)

    3a. 深拷贝快照（以防修改污染原快照）
        enemy  = CopyPlayer(state.Enemy)    → {HeroHealth:28, Mana:4, Hand:3}
        enemyMinions = CopyMinions(...)      → [ {2/3 嘲讽圣盾} ]（全新列表+全新对象）

    3b. 扣费用：enemy.Mana 从 4 → 2
        enemy.HandCount 从 3 → 2

    3c. 对目标随从造成 3 点伤害
        target = enemyMinions[0]  → {2/3, HasDivineShield:true}
        DamageMinion(target, 3)
          → HasDivineShield = true → 抵消本次伤害，移除圣盾
          → 返回新 MinionSnapshot {2/3, HasDivineShield:false}
        enemyMinions[0] = 返回值

    3d. 检查死亡（没有随从死亡，不删除）

    3e. 返回新快照

  Step 4：评分
  Evaluator.EvaluateDetailed(新快照, Enemy视角)

    敌方视角看新快照：
      英雄血量差 = 28 - 30 = -2  → -2 × 2 = -4
      手牌差     = 2 - 对手手牌数  → 按公式算
      场面差：
        敌方场面: [2/3 嘲讽龟 无圣盾] → 2×5 + 3×3 + 3(嘲讽) = 22
        己方场面: [3/2 野猪]          → 3×5 + 2×3 = 21
        场面差 = 22 - 21 = 1

    EvaluationResult { TotalScore: -3 + 手牌分 + 1 }
关键观察：整个过程只有最后一步"评分"是 AI 做决策用的。前 3 步全是数据搬运——拍快照、翻译动作、在副本上执行。真正的 GameManager 从头到尾没被碰过。

6. 涉及的 C# 知识（本项目应用方式）

6.1 static 类 / 静态方法

详细讲解见 CSharpNotes.md: ref 参数 末尾的"当前规则"部分。这里只补充本项目的应用场景。

类为什么用 static
SnapshotSimulator纯函数：输入→计算→输出，不需要"记住"任何状态
SnapshotActionMapper纯翻译器：给定一个真实动作，输出一个快照动作

调用时直接 SnapshotSimulator.Simulate(state, action)，不需要 new SnapshotSimulator()。

6.2 ref 参数

详细讲解见 CSharpNotes.md: ref 参数。本项目在 SnapshotSimulator 中的典型用法：

// 不用 ref：子方法改了 player，调用方看不见
void Foo(PlayerSnapshot player) {
    player = new PlayerSnapshot(...);  // 只改了局部变量
}

// 用 ref：子方法改了 player，调用方的变量也跟着变
void Foo(ref PlayerSnapshot player) {
    player = new PlayerSnapshot(...);  // 调用方的 player 也变了
}

因为 PlayerSnapshot 是不可变对象（改不了字段，只能创建新对象替换），所以需要 ref 来让子方法能替换调用方的变量。

6.3 private set（只读属性）

详细讲解见 CSharpNotes.md: 属性和 private set。

所有快照类都用这个模式：

public int HeroHealth { get; private set; }
//      ↑ 外部能读                 ↑ 只有构造器能写

这样创建后就不能被意外修改，保证了不可变性。

6.4 IReadOnlyList<T> vs List<T>

详细讲解见 CSharpNotes.md: IReadOnlyList 表示外部只读。

// BoardSnapshot 内部用 List（可以 Add/Remove）
private readonly List<MinionSnapshot> playerMinions;

// 对外暴露 IReadOnlyList（只能读 Count 和 [索引]）
public IReadOnlyList<MinionSnapshot> PlayerMinions => playerMinions;

6.5 防御性拷贝

// BoardSnapshot 构造器：把外部传入的列表复制一份，存自己的副本
public BoardSnapshot(IReadOnlyList<MinionSnapshot> player, IReadOnlyList<MinionSnapshot> enemy)
{
    this.playerMinions = CopyMinions(player);  // 抄一份，不存引用
    this.enemyMinions  = CopyMinions(enemy);
}

目的：即使调用方事后修改了它自己的 List，BoardSnapshot 内部不受影响。

6.6 工厂方法 (Factory Method)

以 FromXxx 命名的静态方法，负责创建对象：

GameStateSnapshot.FromGameManager(gm)   // 从 GameManager 创建快照
PlayerSnapshot.FromPlayer(p)            // 从 Player 创建快照
MinionSnapshot.FromMinion(m)            // 从 Minion 创建快照
BoardSnapshot.FromBoard(b, p, e)         // 从 Board 创建快照

好处：构造逻辑集中在 From 方法里，调用方只需要传源对象，不需要知道快照内部怎么组织数据。

7. 游戏开发知识

7.1 为什么 Simulation 不用 MonoBehaviour

所有 Simulation 类都是纯 C# 类（不继承 MonoBehaviour），原因：

  • 不需要挂到 GameObject 上 — 它们不在场景里显示，也不需要 Inspector 配置
  • 不需要 Update/FixedUpdate — 模拟是同步的即时计算，不需要帧循环
  • 可以被快速创建和销毁 — AI 可能对 10+ 个候选动作分别模拟，如果用 MonoBehaviour 会很慢
  • 纯数据 + 纯逻辑 — 更适合做单元测试（以后如果写测试，纯 C# 类比 MonoBehaviour 容易测得多）
面试可讲："AI 模拟层用的是纯数据对象，不依赖 Unity 生命周期。这有两个好处：一是模拟速度快（每帧可以做几十次推演），二是未来要写自动化测试时不需要启动 Unity。"

7.2 数据层和表现层分离

这是游戏开发中的核心架构原则，本项目有两层分离：

  ┌─────────────────────────────────────────────────────┐
  │  第一层分离：Core ↔ UI                              │
  │                                                     │
  │  Core（规则）           UI（显示）                   │
  │  ├ GameManager          ├ GameUIController           │
  │  ├ Player / Board       ├ CardView / HandView        │
  │  ├ Minion / Hero        ├ BoardView / MinionView     │
  │  └ Evaluator            └ HeroView                   │
  │                                                     │
  │  规则：Core 不依赖 UI，UI 可以读 Core。               │
  ├─────────────────────────────────────────────────────┤
  │  第二层分离：真实对象 ↔ 快照对象                      │
  │                                                     │
  │  真实对象（唯一）        快照对象（AI 脑内副本）      │
  │  ├ Player               ├ PlayerSnapshot            │
  │  ├ Minion               ├ MinionSnapshot            │
  │  ├ Board                ├ BoardSnapshot             │
  │  └ GameAction           └ SnapshotAction            │
  │                                                     │
  │  原则：真实对象只有一个。快照可以有很多，互不干扰。    │
  └─────────────────────────────────────────────────────┘

7.3 "轻量化快照"是游戏 AI 的通用做法

不只是炉石 AI 这么做。很多游戏都用类似思路：

游戏类型真实世界快照/模拟世界
炉石类卡牌 GameManager（场上所有对象） GameStateSnapshot（血量/攻击/法力/手牌数）
围棋/国际象棋 棋盘对象 FEN 字符串 / BitBoard 64位整数
RTS（星际争霸） 完整游戏状态 简化的单位/资源摘要（仅 AI 需要的数据）
MOBA（王者/英雄联盟） 完整对局状态 双方等级/经济/位置/塔血量摘要

共性：真实状态很重（很多对象、很多关系），模拟只需要其中一小部分。把这一小部分复制出来、快速推演，是 AI 决策的标准做法。

7.4 阶段性简化 vs 最终架构

当前是阶段性简化，不是成熟项目最终做法。

当前的取舍：
• 快照不模拟战吼/亡语（复杂度高，当前 AI 还用规则选动作）
• 手牌只知道数量（不知道具体牌，评估函数简单）
• 嘲讽在模拟时不检查（模拟攻击时不做目标合法性过滤）
• Simulator 里扣血/死亡/圣盾的处理是硬编码的（几个 if）

面试时这样说：

"快照模拟是第一版，目标是验证'脱离真实状态做推演'这条链路能跑通。目前模拟的粒度和评估函数匹配——评估只看攻击/血量/关键词/手牌数，所以快照就存这些。后续评估变复杂（比如考虑战吼价值），快照再跟着扩展。这样做的好处是每一阶段只增加能解释清楚的复杂度。"

8. 面试问答

Q: 为什么不直接在真实对象上模拟？模拟完再撤回不就行了？

A: 撤回很危险。游戏里有事件系统（比如随从死亡触发亡语），模拟一次可能触发一连串连锁效果，撤回时要把所有状态倒回去——血量、法力、手牌、场面、事件订阅、日志……任何一个漏了就是 bug。而且 Unity UI 是实时刷新的，真实状态每变一次 UI 就会闪一下。快照方案更安全：副本上随便折腾，不影响真实对局一分一毫。
Q: 快照不模拟战吼亡语，AI 的评分不就偏了吗？

A: 对，这是当前版本的已知局限。分两步看：① 当前 AI 选择动作时还没用评分驱动，仍用规则优先级（斩杀 > 解场 > 出牌），所以评分偏差暂不影响决策。② 后续切换到评分驱动时，会优先把战吼亡语加到模拟器里——评估函数和模拟精度要配套升级。
Q: 为什么用索引而不是引用？

A: 快照世界里没有真实对象——PlayerSnapshot 不是一个 Player，MinionSnapshot 不是一个 Minion。如果 SnapshotAction 存 MinionSnapshot 引用，那还说得通；但它需要表达"攻击者是我方场面第几个随从"，而快照里的列表是独立的。用索引最直接：我方场面列表[attackerIndex] 就能拿到攻击者快照。
Q: 以后评估函数变复杂，快照要跟着加多少东西？

A: 看需要什么。比如要评估"手里有没有 AOE"，快照就得知道手牌里每张牌的类型和伤害值。要评估"场上随从的战吼价值"，就得在 GenerateLegalActions 层面算好（因为战吼是一次性的，出牌时就触发了），或者在快照里记录"这个随从有战吼，效果是 X"。关键是按需扩展——评估需要什么数据，快照就抄什么数据，不超前设计。

9. 术语速查

术语含义对应文件/类型
Snapshot (快照) 真实游戏状态的一份轻量副本。只包含 AI 需要的数据，不引用真实对象。 GameStateSnapshot / PlayerSnapshot / MinionSnapshot / BoardSnapshot
Simulate (模拟) 在快照上执行一个动作，返回模拟后的新快照。不修改真实状态，也不修改旧快照。 SnapshotSimulator.Simulate()
Evaluate (评估) 给一个局面打分，正分表示某方优势。支持真实局面和快照局面两种输入。 Evaluator.Evaluate() / EvaluateDetailed()
GameAction (真实动作) 描述一个玩家可以执行的操作（出牌、攻击、结束回合等）。包含对真实对象的引用。 GameAction
SnapshotAction (快照动作) 快照世界的"动作"。用索引和数值代替对象引用。 SnapshotAction
Map (映射) 把真实动作翻译成快照动作的过程。 SnapshotActionMapper.TryMap()
LegalAction (合法动作) 在当前局面下，规则允许执行的动作。AI 从中选择。 GameActionGenerator.GenerateLegalActions()
Immutable (不可变) 对象创建后不能修改。要"改"只能创建新对象。快照对象都用这个模式。 所有 Snapshot 类（private set + 无公开修改方法）
Defensive Copy (防御性拷贝) 收到外部传入的集合时，复制一份自己存，不直接存引用。 BoardSnapshot.CopyMinions()
Factory Method (工厂方法) 以 FromXxx 命名的静态方法，负责创建对象。 GameStateSnapshot.FromGameManager() / PlayerSnapshot.FromPlayer() 等

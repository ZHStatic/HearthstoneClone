# Stage 2 Review

本文档用于阶段 2 收尾复盘：把“法术 + 关键词 + 第一版事件系统”整理成可以演示、可以面试讲清楚、也可以继续扩展到 AI 的阶段成果。

## 阶段 2 目标

阶段 2 的核心不是堆卡牌数量，而是验证三类规则能力：

```text
1. 卡牌可以表达不同类型：随从牌、法术牌。
2. 随从可以拥有关键词，并让关键词影响规则。
3. 某些效果可以由事件触发，而不是写死在单个操作入口里。
```

## 关键代码链路

### 法术

```text
CardData.CardType = Spell
-> GameUIController 进入选目标状态
-> GameManager.TryPlaySpellCardOnMinion / TryPlaySpellCardOnHero
-> Player.PlayCard 扣法力并移除手牌
-> Minion.TakeDamage 或 Hero.TakeDamage
-> CleanupDeadMinions
-> CheckGameOver
```

### 关键词

```text
CardData.Keywords 配置关键词
-> Minion 创建时复制关键词
-> CardView / MinionView 显示关键词
-> GameManager 或 Minion 在对应规则入口识别关键词
```

当前关键词的规则入口：

| 关键词 | 规则入口 | 为什么放这里 |
|--------|----------|--------------|
| 冲锋 | `GameManager.ApplySummonKeywords()` | 冲锋影响召唤后的攻击权限 |
| 嘲讽 | `GameManager.TryAttackMinion()` / `TryAttackHero()` | 嘲讽影响攻击目标合法性 |
| 圣盾 | `Minion.TakeDamage()` | 圣盾影响随从受到伤害时的结果 |

### 战吼

```text
TryPlayMinionCard
-> Board.SummonMinion
-> ResolveAfterSummon
-> ResolveBattlecry
-> 根据 BattlecryType 结算效果
```

当前战吼仍然直接由 `GameManager` 结算，这是阶段性简化。

### 亡语

```text
Minion.IsDead
-> CleanupDeadMinions
-> PublishMinionDied
-> GameEventBus.Publish
-> ResolveDeathrattleOnMinionDied
-> ResolveDeathrattle
```

亡语使用事件系统，是因为死亡来源不固定：攻击、法术、战吼、后续 AOE 都可能导致死亡。

## 架构取舍

当前没有急着拆出 `DamageResolver`、`CombatResolver`、`DeathProcessor` 或完整 `EffectSystem`。

原因：

```text
规则数量还少，先把每条最小链路跑通更重要。
现在过早抽象会让代码变多，但不能立刻带来清晰收益。
```

当前保留的阶段性简化：

| 简化 | 当前合理性 | 后续拆分信号 |
|------|------------|--------------|
| 法术伤害由 `GameManager` 直接结算 | 只有单目标伤害法术 | 出现治疗、Buff、AOE、随机目标 |
| 战吼由 `GameManager` 直接结算 | 当前都是无目标战吼 | 出现需要选目标、复杂条件或多段效果的战吼 |
| 圣盾写在 `Minion.TakeDamage()` | 当前只有一个伤害前修改规则 | 出现免疫、法伤、护甲、吸血、伤害翻倍 |
| 死亡清理由 `GameManager` 处理 | 当前死亡流程短 | 出现亡语连锁、复生、死亡后召唤 |
| UI 手动 `RefreshAll()` | 操作点少，调试直观 | UI 动画、日志、音效和事件驱动刷新变多 |

面试时可以这样讲：

```text
我没有一开始就搭很大的效果系统，而是按功能复杂度逐步拆分。
冲锋和嘲讽先留在 GameManager，因为它们分别影响召唤和攻击合法性。
亡语用事件系统，因为死亡有多个来源。
圣盾先放在 Minion.TakeDamage，因为它是第一个伤害结果修改规则。
等规则数量继续增加，再抽 DamageResolver、CombatResolver、DeathProcessor。
```

## 5 分钟演示脚本

推荐顺序：

```text
1. 打开 BattlePrototype 场景，展示 GameManager 上的双方牌库。
2. Play 后展示手牌、法力、英雄血量和战场区域。
3. 点击费用不足的卡牌，展示非法操作反馈。
4. 打出基础随从，展示扣法力、移除手牌、召唤到场。
5. 打出火花，选择随从或英雄，展示法术目标选择和伤害。
6. 打出疾风斥候，展示冲锋随从召唤后立即 Ready。
7. 展示城墙守卫的嘲讽，让攻击英雄或非嘲讽目标失败。
8. 打出火焰学徒或书卷侍从，展示战吼即时效果。
9. 打出亡语炸弹人并让它死亡，展示 MinionDied 和亡语伤害。
10. 打出圣盾卫士，展示第一次伤害不掉血并失去圣盾，第二次正常掉血。
11. 最后说明 UI 不直接改规则状态，所有操作都通过 GameManager 进入 Core。
```

演示时优先讲“链路”，不要讲卡牌数量。

## 进入阶段 3 前的检查点

进入 AI 前，必须先确认这些事情：

- Core 和 UI 仍然保持单向依赖。
- 当前所有玩家操作都有 `GameManager.Try...` 入口。
- 合法操作判断不能只存在于 UI 层。
- AI 以后要复用玩家操作入口，而不是另写一套规则。
- AI 第一版只做“能玩”，不做复杂智能。

阶段 3 第一件事不应该直接写 AI 搜索，而是先拆“AI 能做哪些动作”：

```text
阶段 3.0：AI 行动建模
-> 定义出牌、攻击、结束回合这些动作如何表示
-> 枚举当前局面下所有合法动作
-> 让 AI 先随机选择一个合法动作执行
```

## 阶段 2 结论

阶段 2 的最小目标已经达成：

```text
卡牌数据可以表达法术、战吼、亡语和关键词。
Core 层可以处理基础出牌、伤害、攻击、死亡和事件触发。
UI 可以展示关键状态，并把玩家输入交给 Core。
项目已经具备进入 AI 阶段的规则基础。
```

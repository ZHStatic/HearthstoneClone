HearthstoneClone 项目整体架构

单人卡牌对战 Demo。当前功能冻结，进入复盘和作品包装阶段。本页用于面试前快速讲清架构、依赖、流程和取舍。

2. 分层总览和依赖方向

UI 层GameUIControllerDeckSelectionControllerViews

显示状态，处理点击，播放表现。只调用 Core，不直接改规则状态。

依赖 Core，读取状态并发起动作
AI 决策层AIControllerActionSelectorEvaluator

生成合法动作，选择动作，解释选择理由，最终仍交给 Core 执行。

使用快照模拟；真实执行回到 Core
Snapshot SimulationGameStateSnapshotSnapshotSimulatorSnapshotFollowUpEvaluator

复制局面数据，在副本上试算动作。快照不持有真实 Player、Card、Minion 对象。

只复制数据，不污染真实局面
Core 层GameManagerActionsEventsLogging

负责规则、状态和结算。Core 不依赖 UI，也不知道按钮、Text、Prefab 和 Canvas。

核心原则：UI 和 AI 可以依赖 Core；Core 不依赖 UI 和 AI。AI 可以在 Snapshot 上模拟，但真实操作必须回到 GameManager.ExecuteAction()。

3. 核心数据链路

卡牌模板到运行时实体

CardData 静态模板
-> Card 手牌 / 牌库实例
-> Minion 场上随从实例

CardData 是 ScriptableObject，只保存名称、费用、攻血、关键词、战吼、亡语和描述等模板数据。运行时费用放在 Card，场上生命、攻击权限和圣盾状态放在 Minion。

套牌数据到玩家牌库

DeckData 预制套牌
-> DeckData.CreateCardList()
-> Player 根据 CardData 列表创建 Card 牌库
-> 抽牌进入 Hand

DeckData 让套牌选择和演示模式不再直接塞散乱卡表到 GameManager，而是通过预制套牌资源开局。

4. 核心流程

开局流程
GameManager.Awake()创建或重置一局游戏。
StartNewGame(playerDeck, enemyDeck, shuffleDeck)读取 DeckData，创建 Player、Enemy、Board。
起手抽牌并进入第一回合UI 在 Start 后刷新当前状态。
出随从流程
点击 CardViewView 只转发 Card。
GameUIController.HandleCardClicked识别随从牌，把请求交给 Core。
TryPlayMinionCardDetailed校验手牌、费用、战场空间和游戏状态。
Player.PlayCard + Board.SummonMinion扣费、移除手牌、创建随从。
ResolveAfterSummon处理冲锋和战吼。
法术、攻击、英雄技能

这三类操作都遵守同一个原则：UI 只记录当前选择状态，Core 决定是否合法和如何结算。

UI 选择状态
-> GameManager Validate / Try...Detailed
-> GameActionResult.Message
-> BattleLogger 记录真实结果
-> UI 刷新并播放表现
死亡和亡语 
DamageMinion
-> Minion.TakeDamage
-> CleanupDeadMinions
-> Publish MinionDied
-> ResolveDeathrattleOnMinionDied
-> BattleLogger
-> CheckGameOver

亡语通过 MinionDied 事件触发，因为死亡可能来自攻击、法术、战吼或未来的其他来源。

AI 回合 
AIController.TakeTurn
-> GameActionGenerator.GenerateLegalActions
-> ActionSelector.SelectAction
-> SnapshotSimulator 试算
-> Evaluator 评分
-> GameManager.ExecuteAction
-> 输出 AI 行动日志

5. 架构亮点

GameAction

把“做什么”抽成数据，玩家和 AI 都能共用。

GameActionResult

Core 返回成功、失败原因和反馈文本，UI 不再自己猜规则结果。

BattleLogger

记录尝试伤害和实际伤害，圣盾抵消时反馈准确。

GameEventBus

保留 MinionDied 事件，让亡语不绑死到攻击或法术流程。

快照模拟

AI 在副本上试算动作，不污染真实对局。

View 复用

手牌和战场 UI 不再每次全量销毁重建，降低 GC 和动画目标不稳定风险。

6. 架构妥协

妥协当前为什么能接受继续扩展时的问题
GameManager 偏重第一个项目优先跑通闭环，集中调度最容易验证。效果和流程继续增加会让方法越来越拥挤。
效果系统未统一法术、战吼、亡语、英雄技能分别验证了不同触发点。大量卡牌会导致分散 switch 和重复结算逻辑。
UI 状态后补先让规则可见、可点，再逐步补反馈和高亮。GameUIController 会承担过多选择状态。
AI 快照和真实规则重复作为 Demo，能清楚展示 AI 思考过程。真实规则每扩展一个效果，快照层也要补近似模拟。
缺少自动化测试早期通过 Play 模式和文档清单验证。后续重构缺少安全网。

7. 如果重做第二版

TurnController

专门处理回合切换、抽牌、法力刷新和回合开始/结束事件。

ActionExecutor

统一执行玩家和 AI 动作，把执行入口从 GameManager 中拆出去。

EffectResolver

统一处理法术、战吼、亡语、英雄技能等效果描述和执行。

DamageResolver

统一处理伤害、圣盾、免疫、法伤、吸血等伤害修改。

UI 状态机

明确空闲、攻击选目标、法术选目标、英雄技能选目标和对局结束状态。

Core 自动化测试

先测费用不足、嘲讽、圣盾、亡语、英雄技能每回合一次，再谈复杂 UI。

面试收束：这个项目不是商业级炉石框架，而是第一个完整 Unity 卡牌对战 Demo。它的价值在于完整闭环、工程意识和能说清架构取舍。

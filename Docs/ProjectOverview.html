🔑 四条核心规则：

💡 为什么分三层？
CardData 是策划配置（一个 asset 可以生成无数张卡），Card 是手牌临时状态（费用可以被修改），Minion 是战场实时状态（血量会变、会死亡）。如果混在一起，就无法实现「减费法术」或「同一张卡打出多个随从」。

5.3 快照模拟三层体系

AI 不能直接在真实游戏上「试走」——试完没法回退。所以设计了三层结构。

PlayerSnapshot
BoardSnapshot

🔑 为什么快照里用索引而不用引用？
快照模拟会「杀死」随从或「打出」手牌，对象数量会变。用索引（int）可以安全地表达「第 3 张手牌」或「第 2 个敌方随从」。用引用（Card 对象）的话，模拟中对象可能变成 null 或指向错误的东西——索引没有这个问题。

5.4 Evaluator 评分公式

AI 用同一套公式评估真实局面和快照局面。正分 = 被评估方有优势。

TotalScore = HeroHealthScore + HandScore + BoardScore
HeroHealthScore = (己方英雄血量 − 敌方英雄血量) × 2
HandScore = (己方手牌数 − 敌方手牌数) × 4
BoardScore = 己方场面价值 − 敌方场面价值
单个随从价值 = 攻击力 × 5 + 当前血量 × 3 + 关键词加分
嘲讽 Taunt：+3  |  圣盾 DivineShield：+5  |  冲锋 Charge：+2

评分权重直观对比（典型中期场面）

英雄血量差
×2 · 波动范围小
手牌数量差
×4 · 只看数量
场面随从差
攻 × 5 + 血 × 3 · 影响最大

💡 场面是评分的主导因素。一个 3/4 随从 = 3×5 + 4×3 = 27 分，相当于 13 点血量差或 6 张手牌差。

5.5 AI 选择原因速查

枚举值含义触发条件
Lethal 斩杀 动作伤害 ≥ 敌方英雄当前血量（且目标不是自己英雄）
HighestEvaluationScore 最优评分 模拟后评分 ≥ 当前评分，且是候选中最高的
AcceptableScoreLoss 可接受亏分 模拟后评分 < 当前评分，但损失 ≤ 3 分（用小亏换节奏）
NoProfitableActionEndTurn 无利可图 所有主动动作评分损失都 > 3 分，只能结束回合
FallbackPriority 兜底优先级 快照模拟不可用（Mapper 失败等罕见情况），退回固定排序
🎯 AllowedScoreLoss = 3 是当前最关键的调参入口。
设为 0：AI 绝对不主动亏分 → 过于保守，几乎只会 EndTurn
设为 10：AI 愿意接受明显亏损 → 过于激进，可能送怪
当前 = 3：折中值，允许用很小的代价换场面节奏。后续根据测试调整。

📐6. 设计模式速查表

这些不是死记硬背的「八股」，而是反复出现的解题套路。看懂它们，代码就不再是一团乱麻。

🏭 Factory Method · 工厂方法
Snapshot 系列 所有 FromXxx() 静态方法
解决什么问题：创建对象的过程很复杂（要从多个地方收集数据、做防御性拷贝），把这些逻辑封装在一个方法里，调用方一行搞定。
// 一行调用，内部做了十几个字段的复制
GameStateSnapshot snap = GameStateSnapshot.FromGameManager(gm);
MinionSnapshot ms = MinionSnapshot.FromMinion(minion);
BoardSnapshot bs = BoardSnapshot.FromBoard(board, p1, p2);
📸 Snapshot / Memento · 快照 / 备忘录
AI 模拟层 GameStateSnapshot 全系列
解决什么问题：AI 需要「试走」一步看结果，但不能真的改游戏状态。拍一张快照 → 在副本上试 → 试完扔掉副本。真实状态纹丝不动。
// 真实状态完全不受影响
var copy = GameStateSnapshot.FromGameManager(gm);
var result = SnapshotSimulator.Simulate(copy, action);
// copy 还是原样，result 是全新的快照
🔒 Immutable Object · 不可变对象
所有 Snapshot 类 GameAction GameActionResult
解决什么问题：对象创建后不能修改。任何「修改」都返回新对象。避免了「A 改了共享数据导致 B 出 bug」的连锁反应——这在 AI 模拟中尤其致命。
// GameAction 创建后不可改，没有 setter
var action = GameAction.CreatePlayMinionCard(card, player);
// 没有 action.Card = otherCard; 这种写法

// SnapshotSimulator 也是：输入不变，返回新快照
📡 Event Bus / Observer · 事件总线 / 观察者
GameEventBus ← MinionDied → GameManager 订阅
解决什么问题：「随从死亡」的触发方式有很多（攻击、法术、战吼…），但触发者不需要知道谁关心死亡事件（亡语）。发布方和订阅方完全解耦。
// 发布方：我只管喊一声
EventBus.Publish(new GameEvent(MinionDied, deadMinion));

// 订阅方：我只管收到后做什么
EventBus.Subscribe(MinionDied, ResolveDeathrattleOnMinionDied);
🎯 Strategy · 策略模式
ActionSelector 三级选择
解决什么问题：选动作的逻辑有三个版本（斩杀 / 评分 / 兜底），每个版本独立封装。改评分阈值不影响斩杀逻辑，加新策略不影响旧策略。
// 三个策略独立，按优先级依次尝试
if (TryFindLethalAction(...))           return;
if (TryFindBestEvaluatedAction(...))    return;
return SelectHighestPriorityAction(...);
⚡ Command · 命令模式（简化）
GameAction + ExecuteAction()
解决什么问题：把「做什么」和「怎么做」分开。GameAction 只描述意图（打哪张牌、打谁），GameManager 负责执行。AI 和玩家 UI 共用同一条执行链路。
// AI 和 UI 都用完全相同的代码执行动作
GameAction action = GameAction.CreateAttackMinion(attacker, target);
GameActionResult result = gm.ExecuteAction(action);
📋 Template / Instance · 模板与实例分离
CardData (SO) → Card / Minion
解决什么问题：卡牌的固定属性只配一次（CardData），运行时实例各管各的状态（CurrentCost、CurrentHealth），互不干扰。这是卡牌游戏最基本的数据架构。
// 同一个 CardData 可以生成多张独立的 Card
Card c1 = new Card(cardData);  // CurrentCost = 3
Card c2 = new Card(cardData);  // CurrentCost = 3
c1.CurrentCost = 2;            // 只影响 c1，c2 不受影响
📦 Partial Class · 分部类
GameManager.cs + GameManager.BattleLog.cs
解决什么问题：GameManager 太长（几百行），用 partial class 把日志相关方法拆分到独立文件。编译时合并成一个类。注意：这只是文件级别的组织手段，不是真正的职责分离。
// GameManager.cs — 回合流程、出牌、攻击、死亡清理
public partial class GameManager : MonoBehaviour { ... }

// GameManager.BattleLog.cs — 日志记录、伤害 helper
public partial class GameManager { ... }
